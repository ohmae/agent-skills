# Kotlin のパフォーマンス上の問題と対策

静的解析で確認する問題と対策をまとめます。メモリアクセスと CPU キャッシュ局所性を優先して確認します。

## メモリアクセスと CPU キャッシュ局所性

頻繁に使うデータの量や走査順序によって、メモリの待ち時間や転送量が処理時間を左右します。データの配置と、実際にアクセスする範囲・順序を確認します。

### ループの処理順序とストライド

物理配置に対してストライドが大きいと、読み込んだキャッシュラインの一部しか使えないことがあります。行優先の画像や行列なら、行内を連続して走査する順序を候補にします。複数の入力で有利な方向が異なる場合は、一定範囲ずつ処理する方法も比較します。表現を変える場合は変換コストも含めます。

```kotlin
// 行単位で保持されたデータを列方向に走査
fun sumGridColumnMajor(grid: Array<IntArray>, width: Int, height: Int): Long {
    var sum = 0L
    for (x in 0 until width) {
        for (y in 0 until height) {
            sum += grid[y][x]
        }
    }
    return sum
}

// 行優先でフラットに格納したデータを連続走査
fun sumGridRowMajor(grid: IntArray, width: Int, height: Int): Long {
    var sum = 0L
    for (y in 0 until height) {
        val rowOffset = y * width
        for (x in 0 until width) {
            sum += grid[rowOffset + x] // 配列の連続した要素を読み込む
        }
    }
    return sum
}
```

### ループ統合

同じ範囲を複数回走査する処理では、中間結果の読み書きとデータの再読み込みが負荷になります。たとえば要素ごとの正規化と集計は、処理順序や副作用が変わらなければ 1 パスにまとめられます。統合で分岐が増える場合や中間結果を別の処理でも使う場合は、複数パスの実装と比較します。

### ポインタチェイシングとデータ構造のフラット化

オブジェクトへの参照をたどる構造では、走査する順序とメモリ上の配置が離れやすくなります。たとえば `Array<Particle>` を頻繁に走査する場合、一部のフィールドだけを読む処理ならフィールドごとのプリミティブ配列（SoA）、複数の値を一緒に読むなら同じ配列に並べる構成が候補になります。2 つの `Int` を `Long` に詰めて `LongArray` に格納する場合は、詰め直すコストや呼び出し側での型変換も確認します。

### メモ化のコスト

ヒット時も、キーやインデックスを求め、保存先から結果を読み出す処理が残ります。たとえば、大きな配列を不規則な順序で参照すると、CPU キャッシュミスによる待ち時間が単純な算術の再計算を上回ることがあります。`HashMap<Int, Int>` ではキーのボクシング、ハッシュ計算、バケットから `Node` や値のオブジェクトへの参照の追跡が重なります。L1 キャッシュで処理できるか主記憶まで読みに行くかで待ち時間は大きく変わります。共有キャッシュでは同期や競合も確認します。

実際の入力サイズ、アクセス順序、結果の再利用頻度を反映した条件で、毎回再計算する実装とメモ化する実装を比較します。ミス時の再計算と格納を含め、必要に応じて構築・更新コストも計測に入れます。

キャッシュや索引を採用する場合は、狭く密な整数キーなら配列を直接参照します。直接参照用の配列が大きくなりすぎる場合は、`androidx.collection` の `IntIntMap`（キーと値が `Int`）、`LongObjectMap`（キーが `Long`、値が参照型）、`ScatterMap`（キーと値が参照型）を比較候補にします。これらはオープンアドレス法を使うフラットなハッシュテーブルで、エントリごとのノードを持ちません。プリミティブ特化型の API を使うと、対応するキーや値のボクシングも避けられます。 [AndroidX Collection API](https://developer.android.com/reference/androidx/collection/package-summary)

### 検索のための索引を作るコスト

索引の構築・更新にかかるコストを、検索で節約できる時間と比較します。たとえば `toHashSet()` で索引を毎回作る場合、検索が数回で終わる、または走査の早い段階で一致することが多いなら、直接走査する方が速いことがあります。既存の索引を再利用できるかも確認します。

## データフロー上のメモリコピー

入力、変換、API 間の受け渡し、出力まで、同じデータがどの表現と領域を経由するか追います。`copyOfRange()`、`copyOf()` のほか、`toList()` と `toIntArray()` の往復や、一時配列に書き出してから出力へ転記する箇所も調べます。呼び出す API が内部でコピーするか確認し、コピーする要素数（バイト数が分かる場合はバイト数）と呼び出し頻度から、削減効果が大きい箇所を選びます。

- 部分データをその場で読み切る処理では、元の配列とオフセット・長さで範囲を渡せるか確認します。バッファのビューを使う場合も、元データの変更がビューに反映される点と、ビューが元の領域を保持する期間を確認します。
- 下流が同じ表現を扱えるなら変換を省きます。変換が必要なら、最終的な表現を要求する境界でまとめて行うか、変換結果を出力先へ直接書き込めるか確認します。
- 作業用バッファの再利用やインプレース更新は、所有権と寿命が明確な場合に検討します。非同期の受け手が消費を終える前にバッファを上書きすると結果が壊れます。独立したスナップショット、呼び出し元からの変更の隔離、API 契約に必要なコピーは維持します。

たとえば、`sumSamples(samples.copyOfRange(start, endExclusive))` で部分配列を作って集計する経路は、集計側が配列を保持せず範囲を読み切るなら、`sumSamples(samples, start, endExclusive)` にできます。空範囲、末尾を含む範囲、無効な範囲の扱いも確認します。

### 割り当て量と保持メモリ

処理中に新しく割り当てる量と、処理後も参照が残って解放できない量を別々に見ます。たとえば大きなバッファの一部を小さなビューとして長く保持すると、ビュー経由で元の領域全体が残ることがあります。元の領域を他で使い続ける必要がなければ、必要な範囲だけをコピーする方が保持メモリを減らせる場合があります。保持元、寿命、同時に保持する件数を確認し、実際の保持条件で比較します。

## コレクションと Sequence

### 多段コレクション操作の実装方法

多段処理では、どの段で中間結果が実体化され、何回走査するかを確認します。たとえば `Iterable.map` と `filter` を連ねると、段ごとに結果リストを作ります。

- 要素ごとの処理が軽く、全件走査するホットパスでは、単一ループへの統合（Loop Fusion）を最初の比較候補にします。`sumOf` など同等の標準 API で 1 パスにまとめられるなら、それも使えます。入力と中間値をプリミティブ型で扱える経路では、段ごとのイテレータ、ラムダの間接呼び出し、中間値のボクシングをまとめて避けられます。
- `first` や `take` で早期終了できる場合や、中間リストが大きい場合は `Sequence` を比較します。遅延評価で中間リストを省けても、段ごとのイテレータ、非 `inline` の変換・絞り込みラムダの呼び出し、ジェネリクスを通る数値のボクシングは残り得ます。`sorted` など全体を保持する操作がある場合は、そのコストも含めます。 [Kotlin の Sequence](https://kotlinlang.org/docs/sequences.html)

走査をまとめたり遅延評価に変えたりすると、変換と絞り込みの実行順序や呼び出し回数が変わります。副作用や例外を含む挙動を確認し、入力規模、絞り込み率、終端操作をそろえて計測します。

次の例では同じ `IntArray` を入力にします。

```kotlin
// 全件を変換してから絞り込む。map で Int をボックス化し、各段で中間リストを作る。
val eagerSum = values.map { it / 2 }.filter { it > 0 }.sum()

// 中間リストを省く。イテレータとラムダ呼び出しを経由し、数値はボックス化される。
val sequenceSum = values.asSequence().map { it / 2 }.filter { it > 0 }.sum()

// 配列を直接走査し、プリミティブのまま集計する。
var loopSum = 0
for (value in values) {
    val half = value / 2
    if (half > 0) {
        loopSum += half
    }
}
```

### コレクションの初期容量

バッファやコレクションを段階的に拡張すると、再割り当てやコピーが起きることがあります。最終サイズを見積もれる場合は `ArrayList(expectedSize)` などで初期容量を指定できます。指定値の意味は API ごとに確認し、見積もりが過大な場合のメモリ使用量も比較します。

### プリミティブ配列

数値データを `List<Int>` や `Array<Int>` に格納すると、ボクシングされた値への参照を扱います。数値の走査や更新が中心なら `IntArray` などが候補です。周辺 API との変換やコピーを含む処理全体で評価します。

## ボクシングとオブジェクト割り当て

短命オブジェクトが多数生成される経路では、割り当てや GC の負荷を確認します。実際の割り当ては、呼び出し方やランタイムの最適化によって変わります。

### 複数値の返却

高頻度で返す結果の割り当てが負荷になっている場合は、結果が呼び出し先の外に保存されるか、保持できる表現は何かを確認します。たとえば `Pair<Float, Float>` では、結果オブジェクトの生成と値のボクシングが発生する経路を調べます。ローカル JVM 計測では、HotSpot C2 が呼び出し先をインライン化し、Escape Analysis とスカラー置換で割り当てを消せる場合があります。実際の呼び出し先をインライン化できない場合や Android の ART では、同じ割り当てが残ることがあります。[ランタイムによる割り当ての違い](micro-benchmarking.md#ランタイムによる割り当ての違い) に沿って対象環境と呼び出し経路を確認します。

- 呼び出し側が結果を保持し続ける必要がなければ、呼び出し側が所有する作業用オブジェクト（例として `PointF`）への書き出しを検討します。
- 2 つの 32 ビット値は `Long` に詰めた `@JvmInline value class` で返す方法もあります。詰め直す処理と、後段のジェネリクスやインターフェース境界でのボクシングも評価します。

```kotlin
// ジェネリックな Pair で座標を返す
fun doublePointSlow(p: PointF): Pair<Float, Float> = Pair(p.x * 2f, p.y * 2f)

// 変更後 A（Out Parameter）。引数で受け取ったインスタンスを再利用して書き込む
fun doublePointOut(p: PointF, out: PointF) {
    out.x = p.x * 2f
    out.y = p.y * 2f
}

// 変更後 B（Packed Value Class）。64bit Long に Float×2 をパックしてプリミティブ返却
@JvmInline
value class PackedPointF(val packed: Long) {
    constructor(x: Float, y: Float) : this(
        (x.toRawBits().toLong() shl 32) or (y.toRawBits().toLong() and 0xFFFFFFFFL)
    )
    val x: Float get() = Float.fromBits((packed ushr 32).toInt())
    val y: Float get() = Float.fromBits(packed.toInt())
    operator fun component1(): Float = x
    operator fun component2(): Float = y
}

fun doublePointPacked(p: PointF): PackedPointF = PackedPointF(p.x * 2f, p.y * 2f)
```

### 可変長引数と配列コピー

Kotlin/JVM では、既存の配列を `process(*array)` で `vararg` に渡すと、通常は呼び出し側に配列全体をコピーするコード（例として `Arrays.copyOf`）が生成されます。複数の配列や個別の要素を混ぜる場合は、たとえば `SpreadBuilder` や `IntSpreadBuilder` が結合用の配列を作ります。ホットループ内で既存の配列をスプレッドする箇所は、配列サイズに比例する余分な処理として優先して確認します。

`process(*intArrayOf(1, 2))` のようにその場で作る配列では、コンパイラが追加コピーを省く場合があります。コピーの有無は対象バージョンの生成コード（例として `javap -c`）で、実際の割り当て量は対象ランタイムの計測で確認します。負荷が大きければ配列や範囲を直接受け取る経路を検討します。既存の `vararg` 版を残すなら、配列版には別名や範囲引数を付けて JVM シグネチャが衝突しないようにします。

### ループや高頻度関数でのインスタンス生成

- 問題: `Regex("...")` や `".*".toRegex()`、`DateTimeFormatter` などを関数やループが呼ばれるたびに生成する。
- 対策。設定と状態を確認し、呼び出し間で安全に共有できるインスタンスを再利用します。たとえば同じパターンの `Regex` を保持する方法や、単純な区切り文字分割に `String.split(',', ';')` を使う方法があります。

### Nullable プリミティブとジェネリクスによるオートボクシング

nullable な数値や、ジェネリクスに渡すプリミティブでは、ボクシングが発生する経路を確認します。欠損を扱う場合、入力として現れない値を予約できればセンチネル値を使えます。値域を維持する必要がある場合は、値と欠損情報を別々に保持する方法も候補になります。

### `@JvmInline value class` と `inline` 関数

- 問題: 型安全性のために導入した ID ラッパー（`data class UserId(val value: Long)`）や単位ラッパー（`data class Meter(val value: Double)`）が大量に生成される。
- 対策。値クラスのまま受け渡せるホットパスでは `@JvmInline value class` によってラッパーの割り当てを減らせることがあります。nullable 型、ジェネリクス、インターフェースとして使う箇所も確認します。ラムダ生成や呼び出しが負荷なら `inline` を候補にし、展開後のコードサイズと実測を確認します。

## アルゴリズムとデータ構造

### 反復する線形探索

1 回に最大 `N` 要素を走査する探索を `M` 回繰り返すと、最悪で `O(N × M)` になります。呼び出し先に隠れた走査も含めて確認します。キーで引く索引や整列済みデータの二分探索などを候補にし、準備・更新コストと、重複や一致順序の扱いを比較します。

```kotlin
// 変更前。O(N * M) — N, M が数千件あると数千万回の比較が発生
fun matchUsers(orders: List<Order>, users: List<User>): List<Pair<Order, User?>> {
    return orders.map { order ->
        val user = users.find { it.id == order.userId }
        order to user
    }
}

// ID が一意なら、キーで引く索引を一度作る
fun matchUsers(orders: List<Order>, users: List<User>): List<Pair<Order, User?>> {
    val userById = users.associateBy { it.id }
    return orders.map { order ->
        order to userById[order.userId]
    }
}
```

### ループ内の文字列結合

- 問題。ループ内で `result += item` を繰り返すと、それまでの文字列を連結のたびにコピーします。同程度の長さの断片を `N` 回追加する例では、コピーする総文字数が `O(N^2)` になります。
- 対策: `buildString` または `joinToString` を使用します。サイズが見積もれる場合は `buildString(expectedCapacity) { ... }` を指定します。

### ソートのコスト

必要な出力を確認します。最小値だけが必要なら走査で求められますし、同じキーを使ったソートを繰り返すなら順序を再利用できる場合があります。全体を整列する場合は標準 API を比較の基準にします。小さな固定長の入力などで専用実装を検討する場合も、安定性や入力を変更してよいかを確認し、実際のサイズと並び順で比較します。

### 呼び出し先で繰り返される処理

比較関数やコールバックに渡した処理は、外側の呼び出しが 1 回でも何度も実行されることがあります。たとえば `compareBy { parseKey(it) }` では、同じ要素のキーも比較のたびに求めます。キー計算に副作用がなく、対象の処理中に結果が変わらないなら、要素ごとに一度だけ計算する方法を候補にします。実際の呼び出し回数を調べ、前処理時間と結果の保持に必要なメモリを含めて比較します。

## 共有状態の競合

共有状態を更新する経路では、ロックを待つ時間とロック内で処理する時間を確認します。共有キューや集計器など、複数の処理が同じ状態に集中する箇所を対象に、単独実行と代表的な並行度でスループットや待ち時間を比較します。競合が大きい場合は、共有状態に依存しない処理をロックの外に出す方法や、局所的に集計してからまとめて反映する方法を検討します。変更前後で更新の原子性、順序、他の処理から結果が見えるタイミングを確認します。

## Coroutines / Flow のオーバーヘッド

非同期処理では、処理単位あたりの起動・切り替え・受け渡しのコストと、上流処理が再実行される回数を確認します。

- たとえば要素ごとの `withContext` や `async` の負荷が大きい場合は、まとめて処理したときの時間と、応答性・キャンセルへの影響を比較します。
- 同じコールド Flow を複数回 collect する場合は、上流の読み込みや計算が繰り返されます。結果の共有を検討するときは、購読ごとの実行が必要か、保持期間や再購読時の動作が変わるかを確認します。
- 生成側と消費側の速度差がある場合は、受け渡しのどこで待ちが生じ、処理待ちの要素が何件残るかを調べます。たとえば消費側が継続して遅い場合、`buffer` の容量を増やすと、消費されるまでの待ち時間や保持メモリが増えることがあります。通常時と負荷が集中する条件で、スループット、端から端までの遅延、滞留量を比較します。溢れたときの動作を変える場合は、要素の欠落が契約上許されるかを確認します。
